# Sentinel Explorer Web — краткое руководство для ИИ

> **Начинай отсюда.** Это компактная точка входа для нового диалога и моделей с малым контекстом. Не загружай всю документацию.

## 1. Что строим

Браузерную ГИС для поиска и просмотра Sentinel-2: карта, каталог сцен, просмотр B02/B03/B04/B08 с независимым назначением каналов RGB, работа с растровыми и векторными данными. Дальнейшие функции — по дорожной карте, не считать их готовыми.

**Критичное требование:** пользователи из России должны иметь возможность искать, просматривать и скачивать снимки без VPN. Это пока НЕ доказано. Российский сервер сам по себе не гарантирует доступ к внешнему источнику.

## 2. Источники истины

При конфликте используй этот порядок и не придумывай решение:

1. Фактический код и тесты — что действительно реализовано.
2. `docs/STATUS.md` — текущее состояние, блокеры и следующая задача.
3. `docs/EXECUTION_PLAN.md` + соответствующая карточка `docs/tasks/PHASE_XX_*.md` — что делать.
4. `docs/DECISIONS.md` — утверждённые решения.
5. Профильные документы — архитектура, API, данные, UX, QA, deployment.

Требования и планы не являются доказательством реализации. Если документы расходятся или решения нет — остановись, опиши противоречие и запроси решение. Не меняй архитектуру молча.

## 3. Начало нового диалога — минимальный контекст

Прочитай только:
1. этот файл;
2. `docs/STATUS.md`;
3. нужный раздел/ID в `docs/EXECUTION_PLAN.md`;
4. одну соответствующую карточку из `docs/tasks/`;
5. только те разделы профильных документов, на которые ссылается карточка;
6. затем изучи существующий код и тесты затрагиваемого модуля.

Не читай все документы и все карточки сразу. Не пересказывай документацию в ответе.

## 4. Как брать задачу

- Выполняй **ровно одну задачу** за рабочую сессию.
- Начинай только со статусом `READY`; все зависимости должны быть `DONE`.
- Если задача `PLANNED`, сначала проверь зависимости и критерии; не объявляй её готовой без оснований.
- До кода: краткий план из 3–7 пунктов, затем минимальные изменения.
- Не расширяй scope, не делай рефакторинг «заодно», не реализуй будущие фазы.
- Если задача требует более 5 production-файлов — остановись и предложи разбить её.
- Не выдумывай API, данные, возможности провайдера или результаты тестов.

## 5. Что обязательно соблюдать

- Production-запросы к поставщикам идут через backend и отдельные provider adapters.
- Используй нормализованную модель Scene и утверждённые API-контракты.
- Базовые каналы: B02, B03, B04, B08; каждый независимо назначается на R/G/B.
- Корректно обрабатывай CRS, nodata, masks, scale/offset и несовпадающие raster grids.
- Не помещай ключи, токены и signed URLs во frontend или логи.
- Соблюдай авторизацию, лицензии, условия кэширования и распространения данных.
- Доступность STAC-каталога не доказывает доступность самих файлов.
- Не заявляй работу без VPN, пока не пройдены проверки из `docs/DATA_ACCESS_RUSSIA.md`.
- NBR требует SWIR; не обещай его на базовом наборе из четырёх каналов.

## 6. Что обновлять после каждой задачи

**Обязательно:**
- `docs/EXECUTION_PLAN.md` — статус задачи: `PLANNED / READY / IN_PROGRESS / IN_REVIEW / DONE / BLOCKED`.
- `docs/STATUS.md` — только если изменились текущая задача, milestone, блокеры или состояние проекта.
- Карточку задачи — результат, фактические тесты, критерии приёмки, известные ограничения и следующий шаг.

**При необходимости:**
- `docs/DECISIONS.md` — только для нового согласованного архитектурного/продуктового решения.
- Контракт/архитектуру/UX/тесты — если задача действительно изменила их; синхронно обнови связанные документы.
- `docs/DATA_SOURCE_TEST_MATRIX.md` — после каждого реального теста провайдера или сетевого маршрута.

Не меняй дату/статус ради видимости активности. `DONE` ставится только после проверки всех acceptance criteria. Если проверка невозможна — `IN_REVIEW` или `BLOCKED`, с причиной.

## 7. Формат отчёта в конце диалога

Кратко сообщи:
1. Task ID и итоговый статус.
2. Что изменено (файлы/модули).
3. Какие команды тестов запускались и точный результат.
4. Какие критерии приёмки подтверждены/не подтверждены.
5. Блокеры и следующий Task ID.
6. Какие документы обновлены.

Не говори «готово», если код не проверен. Не утверждай, что проверил браузер, сервер или доступ из России, если реально этого не делал.

## 8. Стартовая точка проекта

Текущее состояние сверяй прежде всего с `docs/STATUS.md`; краткий ориентир:
- публичный GIS-first лендинг существует;
- frontend scaffold на Vue/Vite/TypeScript и backend scaffold на FastAPI созданы;
- настроены request ID/error contract, health endpoint, Vite proxy и локальный Docker Compose;
- рабочая карта, каталог Sentinel-2, raster viewer и загрузка снимков ещё не реализованы;
- первичный провайдер Sentinel-2 не выбран; доступ к реальным asset-файлам из российского backend и пользовательских сетей без VPN не подтверждён;
- milestone G1 временно разрешён по ADR-010 до первого локального frontend/backend dev-build; G0 остаётся открытым и блокирует provider/raster implementation;
- текущая задача — WEB-01.10 (локальная инструкция запуска), PR #17 находится на проверке. После первого локального dev-build остановиться для российских сетевых испытаний пользователя.

Перед началом всегда перепроверь `docs/STATUS.md` и ветку репозитория: состояние могло измениться.
