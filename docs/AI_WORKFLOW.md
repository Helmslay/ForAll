# Автоматизация работы ИИ-разработчика

Краткий обязательный алгоритм для любой модели, работающей с Sentinel Explorer.

## 1. Подготовка
1. Прочитай `docs/START_HERE.md`, `docs/STATUS.md`, нужный раздел `docs/EXECUTION_PLAN.md` и одну карточку задачи.
2. Проверь актуальную ветку, код и тесты затрагиваемого модуля.
3. Выполняй одну задачу за раз. Начинай только при `READY` и всех зависимостях `DONE`. Иначе зафиксируй blocker.
4. Составь короткий план. Не расширяй scope и не меняй архитектуру/API без согласования.

## 2. Реализация
1. Создай отдельную рабочую ветку от актуального `main`.
2. Изучи только нужные файлы и внеси минимальные изменения.
3. Добавь/обнови тесты. Не используй фиктивные данные в production.
4. Запусти релевантные lint, type-check, unit и integration tests. Запиши точные команды и результаты.
5. Если критерии не выполнены — исправь причину; не маскируй ошибки и не объявляй задачу DONE.

## 3. Pull request и merge
1. Создай PR с кратким описанием изменений, тестов и ограничений.
2. Дождись завершения всех обязательных CI именно для текущего PR head SHA.
3. Проверь mergeable, отсутствие конфликтов, unresolved blocking reviews и requested changes.
4. Если все проверки успешны и изменения в scope — разрешено автоматически слить PR с expected-head SHA и штатным методом репозитория. Отдельное подтверждение владельца не требуется.
5. Если CI отсутствует, pending, failed или результат неоднозначен — не сливай. Найди причину либо оставь blocker.
6. После merge проверь merged state и запиши merge commit SHA.

## 4. VPS и удалённые операции
1. Не считай GitHub-доступ доступом к shell/VPS. Используй удалённый терминал только если он реально подключён и доступен в текущей сессии.
2. До готовности отдельного защищённого терминала VPS-команды выполняет оператор по явно выданным командам. Не утверждай, что выполнил их сам.
3. Не запускай произвольные root-команды. Root-действия — только через отдельное подтверждение, привязанное к точной команде и её параметрам.
4. Для штатного deploy используй только проектный guarded updater. Перед deploy проверь чистоту checkout, целевой commit и backup/rollback-механику.
5. Сначала выполняй изолированные staging-тесты. Не трогай production service, SSH, firewall, пользователей, права, systemd units и secrets без отдельного разрешения.
6. После deploy проверь deployed SHA, тесты, конфигурацию и состояние службы. При ошибке остановись; не заявляй rollback успешным без проверки файлов и реального состояния службы.

## 5. Обязательные границы проекта
- Sentinel-2: B02, B03, B04, B08; каждый канал независимо назначается на RGB.
- Production provider requests — только через backend adapters и нормализованные Scene.
- Корректно обрабатывай CRS, nodata, masks, scale/offset и raster grids.
- Не помещай секреты и signed URLs во frontend, логи, Issues или отчёты.
- Соблюдай авторизацию, лицензии и ограничения поставщиков.
- Доступность без VPN подтверждается только реальными проверками по `docs/DATA_ACCESS_RUSSIA.md`; сервер в России сам по себе ничего не доказывает.
- Не заявляй функции реализованными по плану или макету; сверяйся с кодом и тестами.
- Не заявляй NBR для базовых четырёх каналов: ему нужен SWIR.

## 6. Документация и завершение
После изменения:
- обнови карточку задачи и `docs/EXECUTION_PLAN.md`;
- обнови `docs/STATUS.md`, если изменились текущая задача, milestone или blockers;
- обнови API/architecture/decision docs только при фактическом согласованном изменении;
- после реального теста источника обнови `docs/DATA_SOURCE_TEST_MATRIX.md`.

Финальный отчёт:
- Task ID и статус;
- что изменено и PR/merge SHA;
- точные тесты и результаты;
- acceptance criteria: PASS / FAIL / NOT TESTED;
- blockers/ограничения;
- следующая задача.

Статус `DONE` — только когда все критерии приёмки проверены. Иначе `IN_REVIEW` или `BLOCKED`.


## 7. Ещё не реализованные этапы автоматизации
Не считать эти возможности доступными, пока соответствующие задачи не закрыты и не проверены:

1. **Реальный systemd rollback drill** в отдельной временной staging unit на VPS — ещё не выполнен. Текущие staging-тесты подменяют systemctl/systemd-run.
2. **AGENT-TERM-READY-01** — закрыть readiness gates: guarded deploy/rollback, диагностика VPS, совместимость state, проверка GitHub repo ID, numeric actor ID и минимальных permissions отдельной очереди.
3. **AGENT-TERM-01** — только после READY реализовать отдельный terminal worker под sentinel-ops, GitHub Issues command queue, ограниченные shell-сессии, аудит и fail-closed.
4. **Root broker** — отдельное независимое одноразовое подтверждение root-команд; GitHub Issue/comment не является вторым фактором. WebAuthn/passkey требует отдельного согласования.
5. После реализации — staging, rollback, проверка ограничений и end-to-end тест с мобильного клиента. До этого не заявлять, что ChatGPT имеет прямой VPS shell.

Порядок продолжения: реальный systemd rollback → завершить AGENT-DEPLOY-02 → AGENT-TERM-READY-01 → AGENT-TERM-01. Не перескакивать через зависимости.
