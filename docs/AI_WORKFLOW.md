# Правила работы ИИ-разработчика

Обязательно для любой модели, работающей с этим репозиторием. Документ рассчитан на модели с небольшим контекстом.

## 1. Главное правило
Бери ровно одну задачу из EXECUTION_PLAN.md и соответствующей PHASE карточки. Не реализуй весь этап за один запрос. Не переходи к следующей задаче, пока текущая не проверена.

## 2. Минимальный контекст
Перед работой прочитай:
1. этот документ;
2. docs/EXECUTION_PLAN.md;
3. нужный docs/tasks/PHASE_XX файл;
4. только те sections архитектуры/API/UX/data, на которые ссылается карточка;
5. фактически существующий код затрагиваемого модуля.

Не загружай все docs без необходимости.

## 3. Перед изменениями
1. Убедись, что задача READY.
2. Проверь все зависимости.
3. Просмотри фактическую структуру репозитория.
4. Прочитай существующий код и тесты модуля.
5. Составь план из 3–7 пунктов.
6. Если контракт противоречив — остановись и зафиксируй blocker; не угадывай.

## 4. Размер задачи
- Одна задача — одна законченная функция, компонент, адаптер или тестовый модуль.
- Ориентир — 1–3 production files плюс тесты.
- Если нужно больше пяти production files, сначала предложи декомпозицию и обновление плана.
- Не переписывай файл целиком ради локальной функции.
- Не делай массовое форматирование.
- Не меняй соседние функции без доказанной необходимости.

## 5. Требования к коду
- TypeScript strict mode.
- Python type hints для публичных функций.
- Небольшие функции и понятные имена.
- Валидация входа на границе API.
- Явная обработка ожидаемых ошибок.
- Никаких пустых catch/except.
- Без случайных зависимостей.
- Нет secret keys/passwords/signed URLs во frontend.
- Никаких фиктивных данных в production path; test fixtures допустимы только в тестах.

## 6. Геоданные
- Явно указывать CRS.
- bbox order: west, south, east, north.
- Не угадывать CRS.
- Учитывать nodata, masks, scale и offset.
- Не перепутывать B02/B03/B04/B08.
- Учитывать разницу grid/metadata.
- Проверять geotransform/CRS экспорта.
- STAC search success не доказывает доступность asset.

## 7. Сетевой код
- Только известные provider endpoints из config/adapter.
- Connect/read timeouts и ограниченные retries.
- Не повторять бесконечно.
- Не логировать токены/подписанные URL.
- Проверять content type/size/Range.
- Безопасно обрабатывать redirects.
- Не обходить auth, geoblock, санкционные или договорные ограничения.

## 8. Проверки
Запустить formatter/linter, type check, unit tests модуля, integration tests при изменении API/data flow, доступные regression tests. Если тест не запускался, точно написать почему. Не заявлять, что все тесты прошли, если они не запускались.

## 9. Документация
Обновлять docs при изменении API, config, UX, architecture, data source/terms или статуса задачи. Не дублировать всю архитектуру в комментариях.

## 10. Статусы
PLANNED, READY, IN_PROGRESS, IN_REVIEW, DONE, BLOCKED. ИИ не отмечает DONE, если тесты или критерии не выполнены.

## 11. Финальный отчёт

    Task: WEB-XX.YY
    Status: IN_REVIEW или DONE
    Changed files:
    - path — что изменено

    Implementation:
    - что сделано

    Tests:
    - команда — результат

    Acceptance criteria:
    - пункт — PASS/FAIL/NOT TESTED

    Risks / blockers:
    - список или "нет"

    Next task:
    - ID следующей задачи, только если зависимости позволяют

## 12. Готовый prompt

    Ты работаешь в репозитории Sentinel Explorer.
    Прочитай docs/AI_WORKFLOW.md, docs/EXECUTION_PLAN.md
    и указанный PHASE-файл.
    Выполни только задачу WEB-XX.YY.
    Сначала проверь зависимости и существующий код.
    Не выходи за Scope задачи и не переписывай соседние модули.
    Следуй architecture и API contracts.
    Добавь тесты, запусти проверки, сообщи точные результаты.
    Не используй mock данные в production коде.
    Не отмечай задачу DONE, если критерии не пройдены.
    В конце выведи отчёт по шаблону AI_WORKFLOW.md.

## 13. Если задача слишком сложная
Разбей её на меньшие задачи: модель/тип, pure helper, adapter, API endpoint, UI component, tests. Предложи новые ID, зависимости и критерии; обнови EXECUTION_PLAN до начала реализации.
